# Security Policy — Ritual

**Project:** Ritual — an offline-first habit tracker with streaks

## 1. Reporting a vulnerability

**Please do not open a public issue for a security problem.** A public report describes the flaw to everyone at the same time it warns the people who could exploit it, and this app has no server to patch quickly.

1. Email **`<support@example.com>`** with:
   - a short description of the issue and the affected version/platform;
   - steps to reproduce, a proof-of-concept, or a screenshot/recording;
   - your GitHub handle or name if you want attribution, and "no attribution" if you prefer anonymity.
2. You will receive an **acknowledgement within about 72 hours** (working days; this is a solo-maintained project, so treat that as a target rather than an SLA).
3. If the report is accepted, a fix ships in the next release; the CVE/disclosure timing is coordinated with you where possible.
4. Public disclosure is welcome after 90 days without a fix, or earlier if we agree on a date.

**Out of scope:** findings that require physical possession of an unlocked device the user has handed you; social engineering of the maintainer; issues in an app you built from this source with your own modifications; scanner-generated dependency advisories with no reachable code path.

## 2. Safe harbour

Activities conducted in good faith as part of reporting to this policy are considered authorised. Specifically, when you research and report a vulnerability to this project:

- we will not initiate or support legal action against you over your responsible research;
- we will not ask you to pay for damages, legal fees or other costs related to your report;
- if your activities are limited to this policy, we consider your research authorised and will treat it as helpful rather than hostile;
- we will keep your report confidential and will not report your identity to third parties without your permission, except where legally required;
- if you find a vulnerability in an additional product of ours covered by this policy, please report it and we will extend the same safe harbour;
- we are not able to grant permissions beyond the scope of this policy — you are responsible for obtaining permission from the owner of any device, account or data you do not own.

If you receive legal action related to your research, let us know and we will state that your research was authorised under this policy.

## 3. Threat model

Ritual's attack surface is unusual because the app never communicates. There is no transport to attack, no session to hijack and no API to abuse; what remains is **the data at rest on the device, the file the user exports, the native surface the app does declare (SQLite, notifications, files, a URL scheme) and the dependency tree.**

| #   | Asset / surface                                                                     | Threat                                                                                                                                                     | Mitigation in this design                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | Residual risk                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Local data at rest** (SQLite file in the app's private sandbox)                   | Extraction by another app, or by anyone holding the unlocked device                                                                                        | OS sandbox isolation plus the platform's own file-level/full-device encryption; no world-readable file; the app writes nothing outside its container except when the user explicitly exports                                                                                                                                                                                                                                                                                                                                                                                                                        | **No app-level encryption.** On an unlocked device, or a rooted/jailbroken one, the history is readable. Accepted deliberately: an encryption key would have to live on the same device, and the product promises zero collection rather than "we keep secrets from you". Optional passphrase-encrypted export is on the roadmap.                                                                                                                 |
| 2   | **SQL injection**                                                                   | A crafted habit name, note or imported JSON value altering query semantics                                                                                 | **All value-bearing statements are parameterised** (`runAsync` with `?` placeholders). `execAsync` is used **only** for static DDL and pragmas written as literals in `src/db` — no string interpolation reaches it, ever. User-facing input additionally passes `src/domain/validation.ts` (length caps, `HH:MM` pattern, weekday ranges, colour/icon token allow-lists) before storage. Column/table names come from code, never from data.                                                                                                                                                                       | A future query built by string concatenation would reintroduce the risk. Enforced by review and by the fact that `src/db` is the only module that holds SQL; `npm audit` will not catch it — grep discipline will: `exec`/`runAsync` call sites are small and reviewable.                                                                                                                                                                         |
| 3   | **Malicious or corrupt import file** (JSON backup, `ritual://` launch)              | Import writing out-of-range values, absurd dates, huge arrays, or rows that break invariants                                                               | `parseBackup` in `src/domain/backup.ts` checks the `ritual.backup` schema tag and version, and validates every habit and completion through the same domain rules as the editor (name length 1–48, colour/icon tokens, frequency target 1–7, unique weekdays, real calendar dates — `fromISODate` rejects impossible values like `2026-02-30`). `applyBackup` runs in one exclusive transaction with bound `?` parameters, uses `ON CONFLICT(habit_id, local_date) DO NOTHING` so a second import of the same file is a no-op, and the `replace` mode wipes inside that same transaction rather than file-by-file   | An `import … replace` on a hostile file can still erase the user's own history — it is the user's deliberate action, but the confirmation UI around it is the real control, and it should be loud. Unbounded file size is the weak point: a multi-megabyte `habits` array is valid but silly, so bound the parse and prefer rejecting over partially importing. Everything stays on the user's own device, so the blast radius is their own data. |
| 4   | **OS-level backup extraction** (iCloud / Google One device backup)                  | A cloud account compromise, or an acquirer of the account, obtains the sandbox copy the app never transmitted                                              | Nothing in the app's control: the app has no credentials to revoke and no server record to delete. Documented in the [privacy policy §4](./legal/PRIVACY_POLICY.md#4-where-the-data-lives-and-the-backup-caveat) and the [data-safety sheet](./legal/DATA_SAFETY.md), so users can turn app backup off; data is minimal (habit names, dates, ≤140-char notes, no identifiers, no location, no credentials)                                                                                                                                                                                                          | **Highest-realism risk in this model.** The mitigation is user configuration plus data minimisation, not code. A future encrypted export addresses exactly this scenario.                                                                                                                                                                                                                                                                         |
| 5   | **Exported files left in shared storage** (JSON/CSV via the OS preview/share sheet) | A copy sitting in the app's `exports/` folder, in Downloads, or in a cloud folder becomes readable to others                                               | Export is an explicit user action. The app writes into its own document folder (`exports/ritual-backup-<timestamp>.json`, `exports/ritual-checkins-<timestamp>.csv`) and then presents the OS preview/share sheet; it never uploads or syncs the file itself                                                                                                                                                                                                                                                                                                                                                        | Two residual risks: the export copies **stay in the sandbox** until the user deletes them, and once shared they leave the app's protection entirely. Habit names such as "Therapy" or "Quit smoking" are the sensitive payload — the export screen copy should say plainly that the file is a plain-text copy.                                                                                                                                    |
| 6   | **Deeplink / URL scheme `ritual://` abuse**                                         | Another app launches Ritual with hostile params; a link in a browser triggers an unintended action                                                         | The scheme is declared for configuration completeness but **no route accepts untrusted input and no scheme handler performs a state change** (no delete, no import-from-URL, no navigation with elevated effect). There is no `Linking` subscription or React Navigation `linking` configuration in `src`. Any future handler must validate against the typed param list, ignore unknown keys, and never treat a path or URL supplied by the caller as a file location                                                                                                                                              | `LaunchAppWithoutUserInteraction`-style annoyances (a site repeatedly opening the app) cannot be prevented from within the app; keep handlers side-effect-free so a spam link is at worst a foreground interruption.                                                                                                                                                                                                                              |
| 6b  | **Outbound links opened from Settings**                                             | A wrong or hijacked destination URL sends the user to a page that is not the real policy, or a link built from app data leaks information to a third party | Settings uses `Linking.openURL` (React Native core) for two **hard-coded, constant** URLs: the privacy policy and the terms of service. No parameter is ever interpolated into them, no `canOpenURL` probing of other apps, no URL is opened programmatically at launch, and the app's own data is never appended to the query string                                                                                                                                                                                                                                                                               | The URLs in the source are placeholders (`https://example.com/...`) that must be replaced with the real hosted pages before submission — a store reviewer will open them, and so will users. A user who taps one does leave the offline bubble, so the link should be visually labelled as opening a browser.                                                                                                                                     |
| 7   | **Notifications**                                                                   | A remote payload delivering content the app did not generate; notification content leaking on a lock screen                                                | **There is no push channel at all**: no APNs/FCM registration, no tokens, no remote-notification entitlement or background mode, no service extension. All reminders use locally scheduled triggers (`expo-notifications`) that the OS fires on-device. Notification permission is only requested when the user enables a reminder                                                                                                                                                                                                                                                                                  | A local notification body is generated from the user's own habit name, so a shoulder-surfing or lock-screen read reveals what the app already shows openly. Mitigation is user-side (hide previews in OS settings) — worth noting in Settings copy.                                                                                                                                                                                               |
| 8   | **Dependency risk / supply chain**                                                  | A malicious or vulnerable transitive npm package, or a package that adds a network permission silently                                                     | Renovate-free but regular updates via [Dependabot](./.github/dependabot.yml) (npm weekly, Actions monthly); `npm ci` from a committed lockfile in CI; `npm audit`/`npm audit --omit=dev` as a scheduled check; **`expo-doctor` in CI** ([`.github/workflows/ci.yml`](./.github/workflows/ci.yml)) to catch SDK-version and config problems; dependency list kept intentionally small (see [ADR 0002](./docs/adr/0002-expo-sqlite-over-async-storage-or-watermelondb.md)); no postinstall-heavy or remote-fetching libraries by preference; new runtime deps require an ADR per [CONTRIBUTING.md](./CONTRIBUTING.md) | A compromised maintainer of an approved Expo module could still ship bad code; the app's build is not reproducible-by-default for a user. Post-build verification (checking the prebuilt Android manifest for a new `INTERNET` permission) is the practical tripwire — it is a checklist item in [legal/APP_STORE_CHECKLIST.md](./legal/APP_STORE_CHECKLIST.md).                                                                                  |
| 9   | **CI / build pipeline**                                                             | Secrets leaked in build logs; an unsigned or dev-flagged artifact reaching a store                                                                         | Secrets only in GitHub Actions/EAS, never in the repo (`.env` is git-ignored; [`.env.example`](./.env.example) documents the shape); `release.yml` performs **no** EAS build and assumes no tokens; CI runs tests/lint/typecheck/doctor only; production builds come from a tagged commit through the `production` profile in [`eas.json`](./eas.json)                                                                                                                                                                                                                                                              | A GitHub Actions `pull_request_target`-style workflow with a token would change this risk entirely; none exists, and adding one needs review.                                                                                                                                                                                                                                                                                                     |
| 10  | **Exposure of the source itself**                                                   | A reader of this public repo learns the schema and the file layout, easing an attack on a specific device                                                  | Accepted knowingly: MIT-licensed, no secrets in the repo, no security by obscurity claimed anywhere. The protection is OS-level sandboxing plus the fact that a targeted attack needs the physical device, at which point the app-level cipher (absent) would be the only remaining question — see row 1                                                                                                                                                                                                                                                                                                            | The data values themselves are the secret; nothing in the repo reveals them.                                                                                                                                                                                                                                                                                                                                                                      |
| 11  | **Device loss / theft**                                                             | Full read of habit history and notes                                                                                                                       | Device passcode + platform encryption are the only gate; the app adds no in-app lock or biometric gate                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | **Not mitigated by the app.** Stated plainly in [TERMS_OF_SERVICE.md §7](./legal/TERMS_OF_SERVICE.md#7-your-data-and-the-risk-of-losing-it) so no user assumes a second layer exists.                                                                                                                                                                                                                                                             |
| 12  | **Data integrity over time**                                                        | Silent corruption after a failed migration or a partial write                                                                                              | Forward-only, transactional, immutable migrations keyed on `PRAGMA user_version`; no destructive migration in a released app; SQL uniqueness constraints; export as recovery path                                                                                                                                                                                                                                                                                                                                                                                                                                   | A bug in a migration can be unrecoverable for the user; the mitigations are process-based (migration tests from `version - 1`), as required in [CONTRIBUTING.md §6](./CONTRIBUTING.md#6-adding-a-migration).                                                                                                                                                                                                                                      |

## 4. Deliberate absences, and why they are not vulnerabilities

| Missing control                                                 | Why its absence is acceptable here                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| --------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| App-level database encryption                                   | The key would have to be stored on the same device, which yields protection only against an attacker who can read files but cannot execute the app's own key retrieval. The real controls are the OS sandbox and device encryption. Adding a cipher would also change the store export-compliance answers ([DATA_SAFETY.md §4](./legal/DATA_SAFETY.md#4-the-exportimport-compliance-statement-both-stores-ask-about)), which is a documented cost rather than a hidden one. |
| Network transport security (TLS, pinning, certificate handling) | There is no network traffic to protect. No `INTERNET` permission is expected in the prebuilt Android manifest — and that expectation is a checklist item to verify, not an assumption.                                                                                                                                                                                                                                                                                      |
| Authentication, sessions, password storage, rate limiting       | There are no accounts to authenticate. Consequently there is also no credential store to leak and no login endpoint to attack.                                                                                                                                                                                                                                                                                                                                              |
| Server-side logging, WAF, vulnerability scanning of an API      | There is no server. Conversely, there is no telemetry, so incident detection depends on user reports.                                                                                                                                                                                                                                                                                                                                                                       |
| In-app lock, biometric gate, auto-hide of notification content  | Not implemented for 1.0; recorded as residual risk in rows 7 and 11 rather than claimed as a feature.                                                                                                                                                                                                                                                                                                                                                                       |

## 6. Hardening checklist for maintainers

```bash
npm audit --omit=dev            # production dependency advisories
npm audit                       # includes dev tooling (CI-only exposure)
npm run doctor                  # expo-doctor: config + dependency health
npm run check                   # lint, types, tests
npm run prebuild                # regenerate native projects to inspect them
```

- [ ] Prebuilt `AndroidManifest.xml`: no `android.permission.INTERNET`, no `AD_ID`, no C2DM/FCM permissions.
- [ ] Prebuilt iOS `Info.plist`: `ITSAppUsesNonExemptEncryption = false`; no `NSUserTrackingUsageDescription`; no remote-notification background mode; no unused privacy-sensitive usage strings.
- [ ] `grep` audit of SQL call sites: every `runAsync`/`getFirstAsync` uses `?` placeholders; `execAsync` receives only literal DDL.
- [ ] No `.env`, keystore, `google-services.json`, provisioning profile or API key in git history.
- [ ] `package-lock.json` committed and `npm ci` used everywhere, so CI resolves the same graph.
- [ ] EAS credentials rotate on schedule; service-account JSON stays outside the repo.
