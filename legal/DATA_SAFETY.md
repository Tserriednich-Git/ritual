# Data Safety & App Privacy declaration guide — Ritual

> **Disclaimer:** This document is a template for a portfolio project and is not legal advice, and it is not a compliance guarantee. Store forms change; every recommendation below should be re-checked against the current Play Console and App Store Connect wording at the moment you submit. Phrases such as "typically" and "as of the current console wording" are deliberate.

**Purpose:** a fill-in reference sheet that maps what Ritual actually does to the exact answers expected in the **Google Play Data Safety** section and Apple's **App Privacy "Nutrition Labels"**. The app's posture is zero collection, so most answers are a straightforward "Not collected" / "No".

**Bundle id (both platforms):** `dev.gabrielritual.app`

---

## 1. Facts these declarations rest on

1. No backend, no accounts, no analytics, no ads, no tracking SDKs, no crash reporting, no third-party sign-in.
2. All user data lives in one SQLite file in the app's private sandbox on the device.
3. Notifications are scheduled locally with `expo-notifications` triggers; no APNs/FCM registration and no remote payload.
4. App code uses no network permission and performs no uploads or downloads.
5. Export (JSON/CSV) writes a file into the app's own document folder and opens the OS preview/share sheet; import accepts a JSON backup in `merge` or `replace` mode. Both are on-device operations the user initiates.
6. Uninstalling removes the sandbox and therefore all data. On first launch the app seeds three example habits with no check-ins.

If any of those facts changes — a sync feature, a crash reporter, an ad SDK, push notifications — this sheet and the privacy policy must be revised **before** shipping, and both store declarations must be re-answered from scratch.

## 4. The export/import compliance statement both stores ask about

Both consoles ask, in different words, whether the app **encrypts user data** and how data can be **exported or deleted**. Recommended wording, reusable for both forms:

> Ritual performs no network transmission and implements no cryptographic protocol of its own. Encryption, where it exists, is provided exclusively by the operating system: the app's SQLite file lives inside the app's private sandbox, which iOS and Android protect with device-level, user-passcode-gated encryption. The app declares itself exempt from non-exempt export restrictions (`ITSAppUsesNonExemptEncryption = false`) because it uses only standard OS-provided data protection and no proprietary or non-standard cipher. User data may be exported by the user, on the device, as JSON or CSV: the app writes the file into its own document folder and hands it to the operating system's preview/share sheet, from which the user chooses where it goes. A JSON backup may be re-imported, either merged with existing data or as a replacement. All data is deleted when the user uninstalls the app, and individual habits and check-ins can be deleted inside the app at any time. There is no server-side copy of any user data, so no deletion request can ever be necessary.

Notes to keep you honest when the wording shifts:

- The exemption claim is about **cryptography**, not about privacy: it is a statement that no non-exempt cipher is implemented. Do not cite it as "the app is encrypted".
- Exporting to Files/Sharing is an OS-mediated user action, not a data "share" by the developer; if you later add cloud sync, this statement becomes false and both labels must change.
- If you ever adopt a passphrase-encrypted export (on the roadmap), re-check both the exemption answer and the transit-encryption questions before shipping, and update §2 and §3 in the same PR.
